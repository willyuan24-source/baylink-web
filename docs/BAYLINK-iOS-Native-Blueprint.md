## 一、重新定义 BAYLINK iOS App

**一句话定义:**

> BAYLINK 是湾区华人的 AI 本地生活 App——用 BayBay 一句话发出租房、室友、二手、服务需求,用站内私信和联系方式请求安全地建立联系,让"发帖 → 私信 → 交换联系方式"在一个可信的闭环里完成。

拆解这句话的四个承诺:

| 承诺 | 产品机制 |
|---|---|
| 湾区华人 | 中文优先、湾区地区选择、湾区生活指南、本地分类 |
| AI 本地生活 | BayBay 一句话结构化发帖 + 生活任务助手 |
| 安全联系 | 联系方式检测、私密联系方式、三种联系偏好、验证体系、举报/屏蔽 |
| 闭环 | 帖子 → 私信/联系请求 → 联系卡片 → 线下达成 |

## 二、原生 iOS App 的核心使用场景

### 场景 1:新移民刚到湾区,想找房
- **动机**:落地一两周,住在临时住处,每天刷租房信息。
- **第一屏**:首页顶部地区选择(默认"全湾区",引导选南湾/东湾/半岛/旧金山),快捷分类第一位是"租房",下方是最新租房 Feed。
- **最短路径**:首页 → 点"租房"分类 chip → 筛选地区 → 帖子详情 → 点"私信房东"。3 次点击可发出第一条私信。
- **召回 Push**:"你关注的南湾出现了 3 个新租房帖" (P1) ;第一版是"[房东名] 回复了你的私信"。

### 场景 2:留学生找室友
- **动机**:开学前 1–2 个月,预算敏感,希望找到背景相近的室友。
- **第一屏**:快捷分类"找室友" + BayBay 一句话卡片("一句话告诉 BayBay 你想找什么样的室友")。
- **最短路径**:首页 BayBay 卡片 → 输入"9 月入学 SJSU,找女生室友,预算 1200" → BayBay 生成结构化帖子 → 确认发布。1 分钟发出第一帖。
- **召回 Push**:"有人请求获取你的联系方式"——这是最强的召回事件。

### 场景 3:用户想卖二手家具
- **动机**:搬家前清仓,拍几张照片就想卖掉。
- **第一屏**:中央"+"发布按钮显眼;发布页第一步支持"先拍照后描述"。
- **最短路径**:Tab 中央"+" → 拍照/选图(最多 5 张)→ 一句话"IKEA 沙发 9 成新 $120 Milpitas 自取" → BayBay 补全 → 发布。
- **召回 Push**:"有人评论了你的沙发:还在吗?"

### 场景 4:用户想找搬家 / 清洁 / 维修
- **动机**:有具体任务和时间点,要快速找到靠谱的人。
- **第一屏**:快捷分类"本地服务"聚合(搬家/清洁/维修/接送),附分类安全提示入口。
- **最短路径**:分类 Tab → 本地服务 → 浏览服务商帖子(带手机验证/官方认证标识优先)→ 私信询价;或直接发需求帖让服务商来找。
- **召回 Push**:"3 位服务商回复了你的搬家需求"(聚合通知)。

### 场景 5:房东发布出租房
- **动机**:空房要尽快租出去,不想接骚扰电话。
- **第一屏**:发布入口 + "联系偏好"教育:不公开电话,用请求制。
- **最短路径**:"+" → 拍房间照片 → 一句话描述 → BayBay 生成(含租金、地区、入住时间字段)→ 联系偏好选"对方请求后自动发送" → 发布。
- **召回 Push**:"你的出租帖收到 2 个联系方式请求,点击处理"。

### 场景 6:用户不想公开微信,但想安全联系
- **动机**:被骚扰过或有隐私顾虑,想先聊再给微信。
- **第一屏**:帖子详情页的联系卡片区,清楚显示"作者选择:需同意后发送联系方式"。
- **最短路径**:详情页 → "请求联系方式" → 写一句自我介绍 → 等待对方同意 → 联系卡片自动出现在聊天里。
- **召回 Push**:"[用户名] 同意了你的联系方式请求,微信号已发送到聊天"。

### 场景 7:用户收到私信 / 联系方式请求
- **动机**:Push 把他拉回来,处理买家/租客的消息。
- **第一屏**:点 Push 直达聊天详情或请求 Inbox;消息 Tab 有红点 badge。
- **最短路径**:Push → 聊天详情(键盘自动弹起可直接回复);请求类 Push → 请求卡片,"同意 / 先聊聊 / 拒绝"三个按钮一屏内完成。
- **召回 Push**:本场景就是被 Push 召回的核心场景,必须 100% 可靠。

### 场景 8:用户看湾区生活指南后直接发需求
- **动机**:新人不知道流程(考驾照、装宽带、找搬家),先看攻略。
- **第一屏**:首页"湾区指南"横滑入口;指南详情尾部有"直接发个需求帖"CTA。
- **最短路径**:指南详情 → 底部"让 BayBay 帮你发一个需求" → 预填指南上下文 → 发布。指南变成发帖漏斗。
- **召回 Push**:第一版不为指南做 Push;靠指南导流到发帖后,由消息类 Push 召回。

## 三、主流 App 信息架构

### 底部 Tab:保留五 Tab 结构,微调命名

```
[ 首页 ]  [ 分类 ]  [ ➕发布 ]  [ 消息 ]  [ 我的 ]
```

**结论与理由:**

1. **发布按钮居中突出:是。** 用 56pt 圆形品牌绿(#16A66A)按钮,略微上浮出 Tab Bar(参考小红书/闲鱼)。BAYLINK 的供给侧(帖子)是生命线,发布必须是全 App 最显眼的动作。点击后弹出全屏 Sheet 而不是 push,营造"创作模式"。
2. **BayBay 不做独立 Tab。** BayBay 是能力不是目的地。用户的目的是"发帖/找信息",BayBay 应嵌入在:首页卡片、发布流程第一步、详情页浮动入口、指南页。做成独立 Tab 会变成没人点的聊天机器人页。保留一个全局浮动海獭入口(可关)承接"问 BayBay"心智。
3. **分类独立 Tab:是。** BAYLINK 本质是分类信息平台,"我要找 X"是第一心智。分类 Tab = 类目网格 + 每类安全提示 + 类目内筛选(地区/时间/价格)。
4. **Guides 放哪里:** 不占 Tab。三个入口:首页横滑卡片区、分类 Tab 相关类目下的指南条(现有 CategoryGuideStrip 的原生版)、我的页面"湾区指南"入口。指南是冷启动内容,不是高频目的地。
5. **搜索放哪里:** 首页顶部固定搜索栏(占位文案轮播:"搜 南湾一室一厅 / 二手 iPhone / 搬家师傅")+ 分类 Tab 顶部。不做独立 Tab。
6. **消息中心与联系请求合并:** 消息 Tab 内用 segmented control 分三段:**私信 | 联系请求 | 通知**。联系请求同时在私信列表顶部有一个聚合置顶 cell("联系方式请求 (2)"),保证不被淹没。Badge 数 = 未读私信 + 待处理请求 + 未读通知。
7. **我的页面承载信任、安全、设置、验证:** 结构为"身份卡(头像/昵称/徽章)→ 信任中心(手机验证、官方认证、账号等级)→ 我的内容(发布/评论/请求)→ 安全(屏蔽列表、举报记录)→ 设置(通知、隐私、法律文档、删除账号)"。详见第十节。

## 四、原生 iOS 首页设计

设计原则:**不是网页首页的缩放,而是"今日湾区"信息流**。像小红书首页那样有内容温度,像 Marketplace 那样有信息效率。

### 各区块规格

- **顶部状态区**:大标题风格(iOS Large Title 收缩为 inline),左 logo(海獭头像 28pt),中间地区选择,右侧铃铛(通知中心入口,带红点)。
- **城市/地区选择**:点击弹半高 Sheet,选项:全湾区 / 旧金山 / 南湾 / 东湾 / 半岛 / 北湾,支持记忆(存 `/users/me` 的 preferredRegion,新增字段)。切换后 Feed 立即刷新并轻触感反馈(Haptics)。
- **搜索入口**:点击 push 到 SearchView(历史记录 + 热门搜索词 + 分类快捷)。
- **BayBay 一句话发帖卡片**:首页第一张卡。未输入时显示轮播示例文案;点击直接进入发布流程第一步(不是打开聊天)。每天首次打开有轻微海獭动画,不打扰。
- **快捷分类**:两行网格或单行横滑(建议单行 8 个 + "全部"),icon 用 SF Symbols + 品牌色底。
- **热门本地需求**:Feed 顶部内联一条"今日热门"聚合卡(P1);第一版用"官方推荐"代替。
- **官方推荐**:复用 `/posts/featured`,横滑卡片,与指南卡混排,保证首页永远有内容。
- **湾区指南入口**:官方推荐区混排指南卡 + 分类 chips 尾部"📖 指南"。
- **Feed 信息流**:`/posts?region=&category=` 分页;卡片左图(无图则显示分类色块 + icon)右文;显示价格、地区、相对时间、作者徽章、评论数、有用数。
- **空状态**:不出现"没有帖子"的荒地。空 Feed 时显示:官方推荐 + 指南卡 + 一张大的 BayBay 邀请卡("这个分类还没有帖子,发第一帖的人最容易被看到 → 让 BayBay 帮你发")。
- **未登录状态**:首页完全可浏览(逛是转化的开始)。发帖/私信/请求/点赞时触发登录 Sheet(半屏,支持 Sign in with Apple + 邮箱),文案:"登录后就能联系 TA"。
- **登录后状态**:BayBay 卡片带昵称问候;通知铃铛激活;Feed 过滤掉已屏蔽用户(`/users/me/blocks`)。
- **下拉刷新**:原生 `refreshable`,海獭小动画(Lottie 或 SF Symbol 动效)。
- **Skeleton loading**:卡片形状的 redacted placeholder(`.redacted(reason: .placeholder)` + shimmer),首屏 3 张。
- **内容不足时**:三层兜底:①官方推荐永远置顶 ②指南卡混入 Feed(每 6 帖 1 指南)③ BayBay 邀请卡。运营侧保证每个核心分类每周有官方精选。
- **不像 Craigslist 的关键**:图片优先的卡片(而非文字列表)、作者身份与徽章可见(而非匿名)、圆角卡片 + 米白底的温度感、BayBay 的 AI 存在感、安全提示的显性化。Craigslist 是"信息的仓库",BAYLINK 要做"邻里的市集"。

## 五、原生发布流程设计

### 1. 页面流程

```
Tab 中央 ➕
   ↓ (全屏 Sheet)
CreatePostStartView 「一句话告诉 BayBay」
   ├─ 输入一句话 (+可先加图) → [让 BayBay 整理] → BayBayDraftView
   └─ [跳过,自己写] → CreatePostReviewView(空表单)
   ↓
BayBayDraftView 生成中(流式展示字段逐个填充)
   ↓ 自动跳转
CreatePostReviewView 确认与编辑
   ├─ 编辑标题/正文/分类/地区/价格/标签
   ├─ PhotosPicker 选图/拍照(≤5张)
   ├─ 联系方式检测 → 拦截 Sheet「移到私密联系方式」
   ↓
ContactPreferenceView 联系偏好
   ├─ ① 只用站内私信 (dm_first)
   ├─ ② 对方请求后自动发送 (auto_send)
   └─ ③ 我同意后再发送 (manual_approve)
   ↓ [发布]
PostSuccessView 发布成功
   ├─ 引导分享(PostShareSheet 原生版)
   ├─ 引导开启通知(未授权时)
   └─ 安全联系提醒(分类安全提示)
```

### 2. 每一步 UI

**CreatePostStartView**
- 全屏 Sheet,顶部左"取消"、右无按钮。
- 海獭 BayBay 头像 + 一句欢迎:"想发什么?一句话告诉我"。
- 大输入框(多行,自动聚焦),下方示例 chips:"找室友"、"卖二手"、"求搬家师傅"、"出租房间"(点击填入模板)。
- 底部两个按钮:主按钮「✨ 让 BayBay 帮我整理」,次按钮「自己写」。
- 输入框下方可先附图:小的"+ 图片"入口(照顾"先拍照"的二手场景)。

**BayBayDraftView**
- 卡片式流式生成:标题 → 分类 → 地区 → 价格/预算 → 正文 → 标签,逐项打字机效果填充,每项右侧出现 ✓。
- BayBay 补充建议以气泡显示:"建议补充:入住时间、是否包水电"。
- 可随时点「停止」;完成后自动进入 Review。
- 复用 `/ai/post-assist`(建议后端加 SSE 流式返回,见第十六节)。

**CreatePostReviewView**
- 表单式(Form/List 风格),每个字段可点开编辑;BayBay 生成的字段带淡绿色"AI"小标。
- 图片区:横滑缩略图 + "+"(PhotosPicker,`maxSelectionCount = 5 - 已选数`),支持拍照(ActionSheet:拍照/相册),长按拖动排序,第一张为封面。图片本地压缩(对应 web 端 browser-image-compression 逻辑:长边 ≤1600px,JPEG 0.8)。
- 正文编辑时实时联系方式检测(移植 `contactDetection.ts` 的正则:电话/邮箱/微信/关键词)。检测到时输入框下方出现黄色提示条:"检测到微信号,公开展示有风险"。
- 点「下一步」时若仍有联系方式 → 弹拦截 Sheet:
  - 标题:"帖子里有联系方式"
  - 说明:"公开的微信/电话容易被骚扰和爬取。移到私密联系方式后,只有你同意的人才能看到。"
  - 主按钮:「移到私密联系方式」(执行 `analyzeContactsInText` 的 cleanedText 替换正文,检测到的方式自动填入联系偏好)
  - 次按钮:「返回修改」
  - 不提供"坚持公开"选项(与 web 端策略一致,机制不可绕过)。

**ContactPreferenceView**
- 三选一大卡片(radio 卡片,含图标和说明):
  1. 「只用站内私信」— 最私密,别人只能给你发消息。
  2. 「对方请求后自动发送」— 省事,对方点请求就能拿到你的联系卡片。(推荐给房东/卖家)
  3. 「我同意后再发送」— 最可控,每个请求你都亲自把关。(默认选中)
- 选 ②/③ 时展开联系方式编辑(微信/电话/邮箱,可多个,带"仅同意后可见 🔒"标注)。
- 底部主按钮:「发布」。

**PostSuccessView**
- 全屏庆祝页:海獭举牌"发布成功 🎉" + 帖子卡片预览。
- 三个引导(按优先级最多展示两个):
  1. 分享卡片:「分享到微信群,更快找到人」→ 原生 ShareSheet(分享链接 `https://www.baylink.us/posts/:id`,配文案模板)。
  2. 通知未授权时:「开启通知,第一时间知道谁想联系你」→ 触发系统授权弹窗(这是最佳授权时机)。
  3. 安全提示折叠条:按分类显示(复用 `categorySafetyTips`),如租房类:"看房请选白天,勿提前转账定金"。
- 按钮:「查看帖子」/「回首页」。

### 3. 关键按钮文案

| 位置 | 文案 | 备注 |
|---|---|---|
| 入口 | ✨ 让 BayBay 帮我整理 | 不用"生成",用"整理"降低 AI 戒心 |
| 入口次按钮 | 自己写 | 不贬低手写用户 |
| 拦截 Sheet 主按钮 | 移到私密联系方式 | 与 web 端一致的机制名 |
| 偏好③说明 | 我同意后再发送(推荐) | 默认项 |
| 发布 | 发布 | 不用"提交" |
| 成功页 | 分享到微信群 | 直说场景,湾区用户的真实动作 |

### 4. 错误状态

- **BayBay 超时/失败**:气泡显示"BayBay 开小差了",提供「重试」和「自己写」(内容不丢,已输入的一句话带入空表单)。
- **图片上传失败**:缩略图角标 ⚠️,点击重试单张;发布时若仍有失败图,询问"忽略失败图片发布 / 继续等待"。
- **网络失败恢复**:发布请求失败 → 草稿自动落盘(本地 Draft 存储,含图片本地引用),Toast:"已存为草稿,网络恢复后可一键发布";发布页入口显示"草稿 (1)"。
- **草稿**:任何时候点"取消" → ActionSheet:「存草稿 / 不保留 / 继续编辑」。草稿本地存储(第一版不做云同步)。
- **登录过期**:静默刷新失败则弹登录 Sheet,登录成功后继续原发布动作。

`CreatePostStartView` / `BayBayDraftView` / `CreatePostReviewView` / `PhotoPickerSection` / `ContactDetectionSheet` / `ContactPreferenceView` / `PostSuccessView` / `DraftListView`,对应 ViewModel:`CreatePostFlowViewModel`(整个流程一个状态机,枚举 `CreatePostStep`)。

### 设计决策

- **消息分类用 segmented control:是。** 三段:私信 / 联系请求 / 通知。评论回复通知、系统通知、管理员广播都归入"通知"段(通知内部按时间流,类型用 icon 区分:💬评论 ↩️回复 👍有用 🛡️管理员 🔐账号安全)。

### 机制细节

- **请求前说明**:附言 Sheet 顶部一句话:"你的请求和附言会发给作者,作者同意后 TA 的联系卡片会出现在你们的聊天里"。透明的机制说明是信任的来源。
- **复制按钮**:联系卡片每行右侧「复制」,点击后 Haptic + Toast"已复制微信号,去微信添加吧"。这是给微信重度用户的关键顺滑点。
- **安全提醒**:联系卡片底部固定小字 + 同意确认 Sheet 里提示帖主"只发送给你信任的请求者"。
- **隐私说明**:联系方式仅存在于双方聊天;对方举报/被封禁后卡片对其失效(P1:卡片可撤回)。
- **如何让微信重度用户接受这个机制**:关键洞察——湾区华人不是不想用微信,而是**不想把微信号公开给所有人**。所以机制的卖点不是"别用微信",而是"**你的微信只给你选中的人**"。产品语言全部围绕这一点:"不公开,但一键可达微信"。同意后的体验必须比"帖子里贴微信号"更顺:卡片 → 复制 → 跳微信,三步内完成。
- **如何避免用户绕过机制在正文公开微信**:五层防线:
  1. 发布侧强拦截(不可选择"坚持公开",只能移入私密或返回修改);
  2. 移入私密是"更好的默认"而非惩罚(自动填入偏好、文案强调好处);
  3. 服务端二次检测(新增,防绕过客户端);
  4. 评论区软提示 + 举报类型含"公开联系方式";
  5. 教育:发布成功页和指南里持续讲"为什么请求制更安全"(被爬号、骚扰、诈骗案例)。

## 九、BayBay 原生 App 角色设计

**定位:湾区生活任务助手,不是聊天机器人。** BayBay 出现在"用户有任务"的时刻,输出的是结构化结果(帖子草稿、清单、卡片),不是闲聊。

### 各场景的 BayBay

| 场景 | 形态 | 行为 |
|---|---|---|
| 首页 | 一句话发帖卡片 | 输入 → 直接进发布流程;不开聊天窗 |
| 发布 | 流程第一步(核心) | `/ai/post-assist`:生成标题/正文/分类/地区/标签/价格/补充建议 |
| 帖子详情 | 右下浮动小海獭(可关) | 点开 → 针对该帖的快捷问题:"帮我起草询问消息"/"这个价格合理吗"/"约看房要注意什么" |
| Guides | 指南尾部 CTA + 指南内问答 | `/ai/guide-chat`:回答指南相关问题,尾部引导发需求帖 |
| 我的页面 | 不需要 | 我的页面是管理场景,塞 BayBay 是打扰 |
| 消息 | 第一版不需要 | 私信是人与人的场景;P2 可做"BayBay 帮你回复草稿" |

- **视觉入口**:统一用海獭头像 + 淡绿渐变卡;全局只有详情页有浮动入口,避免满屏海獭。
- **语气**:热心靠谱的湾区学长/学姐。中文为主,自然夹英文地名("Milpitas"、"Caltrain")。短句,先给结论再给理由。不卖萌过度,不用"亲"。
- **输出格式**:永远是结构化卡片(字段卡、清单卡、步骤卡),不输出大段散文。每个输出末尾带一个行动按钮("就这样发布"/"发一个需求帖"/"查看指南")。
- **帮助发帖**:补全缺失字段并主动追问最关键的一项("补充入住时间,租房帖回复率高 40%");纠正分类;把口语转成清晰正文;敏感信息移入私密。
- **帮助避免诈骗**:①发布/浏览租房、二手、服务类时输出场景化提醒 ②识别帖子中的风险模式(远程房东、先付定金、价格显著低于市场)时在详情页 BayBay 入口显示"⚠️ 这类帖子请注意…" ③聊天安全提示条的文案由 BayBay 语料统一维护。
- **提升帖子质量**:生成时强制结构(标题含地点+核心信息;正文分段;标签规范化);对模糊帖生成"补充建议"清单。
- **避免生成违规内容**:系统 Prompt 约束(禁代写违规类目:代考、假证、违禁品、成人服务、移民造假);生成后走与人工发帖相同的审核管线(不豁免);检测到违规意图时拒绝并给出社区准则链接;所有 AI 生成帖同样可被举报。

│ 🔒 隐私设置(默认联系偏好)     >  │
│ 🚫 屏蔽列表                  >  │

### 要点

- **头像/昵称**:编辑资料页(EditProfileView)改;头像走图片上传管线。
- **常用地区**:影响首页默认筛选。
- **我的发布**:列表含帖子状态(展示中/已下架/被移除),支持编辑、删除、改联系偏好。
- **我的联系请求**:两个 tab(我发出的/我收到的),状态:待处理/已同意/已拒绝(复用 `/contact-requests?role=&status=`)。
- **手机验证**:VerificationView,复用 `/users/me/phone/start` + `/users/me/phone/verify`;含 SMS 同意文案(SmsConsentView 原生化)。验证成功即得 📱 徽章,文案强调"带验证徽章的帖子回复率更高"。
- **官方认证申请**:OfficialVerificationView,复用 `/users/me/official-verification`;面向服务商/房东,提交材料 → 审核中 → 通过(✓ 蓝绿徽章)。
- **账号信任等级**:第一版只展示徽章集合;等级分(Lv)P1 再做,避免冷启动期等级普遍很低带来的负面感。
- **隐私设置**:默认联系偏好(新帖预填)、是否允许陌生人私信(P1)、屏蔽列表入口。
- **删除账号**:设置内二级页,红色入口。流程:说明后果(帖子/私信/请求将被删除或匿名化)→ 输入密码或重新认证 → 二次确认 →调用删除 API(第十六节新增)→ 本地清空 + 回到未登录首页。**App Store 硬性要求,P0。**

- **管理员账号差异**:🛡️ 徽章全局显示(帖子/评论/私信);我的页多一个"管理入口"(移除帖子、处理举报、发官方通知、精选帖子 `/posts/:id/feature`)。管理功能第一版可继续用 Web 后台,App 端只保留徽章展示。

## 十一、Push Notification 设计

### 分级策略

| 级别 | 事件 | 处理 |
|---|---|---|
| **必须推送** | 新私信;新联系方式请求;请求被同意;管理员通知;账号安全(异地登录/改密) | Push + 站内 + badge |
| **默认推送,可关** | 评论;回复;请求被拒绝(文案柔和) | Push + 站内 |
| **只站内** | 有用点赞(聚合);官方推荐上新;指南更新 | 站内通知段 |
| **不做** | 营销召回、"你可能感兴趣"、每日摘要 | 第一版一律不做 |

- **请求被拒绝**要推(否则请求方一直等待),但文案不用"拒绝":"你的联系请求已有结果,24 小时后可再次请求"。
- **权限请求时机**:绝不在启动时弹。三个触发点(命中其一):①发帖成功页 ②发出第一条私信/请求后 ③收到第一条回复进 App 时。先展示自绘预弹窗("别错过租客/买家的回复")→ 用户点"开启"才触发系统弹窗,保住二次请求机会。
- **推送文案示例**:
  - 新私信:`小王:请问几月能入住?`(标题为帖子名《两室一厅》)
  - 新请求:`有人想获取你的联系方式` / 正文:`Amy 请求联系《两室一厅》,点击处理`
  - 被同意:`小王同意了你的联系请求` / 正文:`联系卡片已发送到你们的聊天`
  - 评论:`你的《IKEA 沙发》有新评论:还在吗?`
  - 管理员:`🛡️ BAYLINK:你的帖子已被精选推荐`
  - 隐私注意:私信 Push 不显示联系卡片内容(微信号绝不出现在锁屏)。
- **点击落点**:见第七节末尾的 DeepLink 表。
- **通知设置页**:分类开关(私信/联系请求/评论与回复/官方通知),账号安全通知不可关。附系统设置跳转(当系统级被拒时显示引导条)。
- **避免骚扰**:同会话私信 Push 1 分钟内合并;同帖评论 5 分钟聚合("3 条新评论");每日非交互类 Push 上限 2 条;晚 11 点–早 8 点非私信类静默(本地时区)。
- **Badge 数字**:App 图标 badge = 未读私信 + 待处理联系请求 + 未读通知(与消息 Tab badge 同源,由服务端 unread-count 接口统一计算,避免客户端算错)。
- **Beta 第一版最低范围**:新私信、新联系请求、请求被同意、管理员通知、账号安全。评论/回复 Push 若来不及可先降级为站内通知。

以现有 web 品牌为基础(直接从 tailwind.config.js 移植),翻译成 iOS 语言:

| Token | 值 | iOS 用法 |
|---|---|---|

| 深绿 `brandGreenDeep` | #128256/#168A58 | 按钮 pressed 态 |

| 米白背景 `cream` | #F7F4EC | 页面背景(温暖感的来源,勿用纯白) |
| 卡片白 | #FFFFFF | 卡片 |

- **字体**:正文用系统字体(SF Pro + PingFang SC 自动回退)——中文 App 用系统字体是最稳的选择;大标题/数字可用 SF Pro Rounded 增加亲和力。web 端的 Plus Jakarta Sans 不必带到 iOS。字阶:LargeTitle 34 / Title 22 / Body 17 / Sub 15 / Caption 13。

- **阴影**:极轻(y2 blur16 黑 5%,对应 web 的 shadow-card);列表卡片可无阴影仅描边,滚动性能优先。
- **Tab Bar**:白底 + 上分割线;选中态品牌绿 icon + 文字;中央发布钮 56pt 圆形绿底白 "+",上浮 8pt。
- **Navigation Bar**:米白底融入背景,Large Title;详情页透明渐变。
- **Sheet**:全部用原生 `presentationDetents`(medium/large),圆角顶部,带 grabber。登录、联系偏好、附言、举报都用 Sheet,减少全屏跳转。
- **Toast**:顶部下滑胶囊式(成功绿/警告黄/错误红 + icon),2 秒自动消失,复用 web Toast 的文案体系。
- **Empty State**:统一模板 = 海獭插画(不同姿势)+ 一句话 + 一个 CTA。空状态是海獭出场的主要舞台。
- **Loading / Skeleton**:首屏 skeleton(redacted + shimmer);操作等待用按钮内 spinner;BayBay 生成用流式打字机(绝不转圈干等)。
- **Badge 体系**(与 UserTrustBadges 对齐):🛡️ 管理员=深绿盾;✓ 官方认证=绿底白勾圆标;📱 手机验证=描边小标。顺序固定:管理员 > 官方 > 手机。徽章在:作者卡、评论、私信列表、请求卡全量展示。
- **安全提醒**:统一淡黄底 #FFF8E6 + ⚠️ + 深棕文字,圆角 12pt,全 App 只有这一种黄,让"黄=注意安全"成为条件反射。
- **联系卡片**:白卡 + 顶部 4pt 品牌绿条 + 📇 标题 + 行式联系方式 + 复制按钮,是全 App 最"贵重"的卡片,视觉上要有仪式感。
- **BayBay 卡片**:淡绿渐变底(#EAF6F0 → 白)+ 海獭头像 + 圆角 20pt,全 App 唯一用渐变的组件,保持 AI 感稀缺性。
- **海獭 mascot 使用场景**(克制原则,全 App ≤6 处):App 图标、启动页、BayBay 入口头像、空状态插画、发布成功页、下拉刷新动画。不在按钮、导航、列表里出现。
- **深色模式:第一版不支持。** 强制 light(`preferredColorScheme(.light)`)。理由:米白暖色体系做深色需要整套推导,收益低于成本;info.plist 声明 light only 不影响审核。P1 再做。
- **温暖可信 + AI 工具感的配方**:温暖=米白底+海獭+圆角;可信=徽章体系+安全黄条+克制的配色纪律;AI 感=唯一的渐变 BayBay 卡+流式生成动效。三者各有专属视觉通道,不混用。

## 十五、SwiftUI 技术架构建议

### 总体架构

**MVVM + Repository,适合。** 单人/小团队 + CRUD 为主的产品,MVVM 足够,不要上 TCA(学习成本与迭代速度不划算)。

```
BaylinkApp/
├── App/            BaylinkApp.swift, AppRouter, DeepLinkHandler
├── Core/
│   ├── Network/    APIClient, Endpoint, APIError
│   ├── Auth/       AuthManager, KeychainStore
│   ├── Realtime/   SocketManager (socket.io)
│   ├── Push/       PushManager, NotificationHandler
│   └── Storage/    DraftStore, UserDefaults wrappers
├── Domain/         Models (Post, User, Conversation, ContactRequest, Comment, Notice)
├── Data/           Repositories: PostRepo, MessageRepo, ContactRequestRepo, UserRepo, AIRepo
├── Features/
│   ├── Home/  Category/  Search/
│   ├── CreatePost/   (状态机 CreatePostFlowViewModel)
│   ├── PostDetail/   Comments/
│   ├── Messages/  Chat/  ContactRequests/  Notifications/
│   ├── Profile/  Verification/  Settings/
│   └── Guides/  BayBay/
└── DesignSystem/   Colors, Typography, BLCard, BLButton, BLBadge, BLToast, BLEmptyState
```

- **APIClient**:URLSession + async/await;`Endpoint` 枚举描述 method/path/body;统一 `Authorization: Bearer <jwt>`;泛型 decode;401 → AuthManager 登出流。基地址与 web 相同:`https://baylink-api.onrender.com/api`。
- **AuthManager**:`@Observable` 单例;登录/注册/登出;token 与 currentUser 缓存;广播登录态给全 App(web 端存 localStorage 的 `currentUser`,iOS 端 token 入 Keychain,profile 存文件缓存)。
- **Token storage / Keychain**:JWT 存 Keychain(kSecAttrAccessibleAfterFirstUnlock);绝不进 UserDefaults。若后端 token 无刷新机制,建议后端加长效 refresh token(见十六节),否则用户频繁重登会杀留存。
- **Socket.io iOS client**:`socket.io-client-swift`;连接参数与 web 端一致(握手带 JWT,connect 后 `join_room`,监听 `new_message`)。App 进后台断开、回前台重连;消息去重靠 messageId。注意 Render 免费实例冷启动会掉线,重连要有退避。
- **PushManager**:UNUserNotificationCenter 授权状态机(未请求/预弹窗已示/已授权/已拒);device token 注册上传(新 API);前台收到 Push 转为应用内横幅;点击解析 payload 里的 deeplink 字段路由。
- **ImageUploadManager**:PhotosPicker(免全库权限)+ Camera;下采样(长边 1600px,JPEG 0.8,对齐 web 压缩参数);并发上传队列 + 单张重试;返回 URL 数组挂到 post payload。
- **NotificationManager**:通知中心数据源 + 未读计数(与 badge 同步,`setBadgeCount`)。
- **ContactRequestManager**:请求状态缓存(pending/approved/declined + cooldownUntil),驱动详情页按钮态。
- **PostStore / MessageStore**:内存缓存 + 轻量磁盘缓存(JSON 文件即可,第一版不用 SwiftData/CoreData);Feed 分页游标管理;乐观更新(点赞、发评论先更 UI 后确认)。
- **Error handling**:APIError 枚举(network/server(code)/decode/unauthorized);ViewModel 统一转用户文案;全局 Toast 通道。
- **Offline / retry**:发帖失败落草稿;聊天消息本地待发队列(状态:sending/failed,点重发);Feed 有磁盘缓存可离线浏览上次内容。第一版不做完整离线同步。
- **Deep link / Universal link**:`baylink://post/:id` 等自定义 scheme + Universal Links(`https://www.baylink.us/posts/:id`, `/guides/:slug`, `/messages`——与 web routing.ts 的路径对齐);AASA 文件部署到 baylink.us;AppRouter 统一解析(Push payload 与 UL 走同一路由表)。
- **App badge**:服务端 unread-count 为准,Push 带 badge 字段,进 App 后主动拉取校准。
- **State management**:iOS 17+ `@Observable`(建议 minimum target iOS 17,湾区用户设备新);全局仅 AuthManager/PushManager/SocketManager/Router 为环境对象,其余状态归 Feature ViewModel。

## 十七、MVP 范围收敛

**第一版必须做(全部 P0):**
原生首页(Feed+推荐+BayBay 卡)、分类、发帖全流程、BayBay 发帖助手、图片上传(≤5)、帖子详情、私信(Socket 实时)、联系方式请求闭环、评论+一级回复、有用点赞、分享(系统 ShareSheet)、Push(5 类核心事件)、我的+手机验证、举报(帖/人/评论)、屏蔽、删除账号、Privacy/Terms/Community Guidelines、指南(可内置数据)。

**第一版明确不做:**
支付、会员、广告、地图(地区用文字选择器,不接 MapKit)、视频上传、群聊、随机聊天/发现人、直播、完整多语言(中文为主,系统级英文局部适配即可)、开放式 AI 聊天机器人(BayBay 只做任务式)、推荐算法(时间倒序+精选即可)、服务评价体系、交易担保、收藏、深色模式、等级分数值化。

**收敛纪律**:凡是"能让列表更好看"的需求让位于"能让一次联系发生"的需求。第一版唯一北极星:**每周成功建立的联系数(私信会话数 + 批准的联系请求数)**。

### 风险与降级

- **最容易延期**:①APNs 全链路(后端管线+前端落点,涉及两端,W1 就要开工,别拖到 W9)②Socket 稳定性(Render 冷启动/重连)③BayBay 流式体验 ④图片上传管线(现有 base64 方案 iOS 不可用,必须新 upload API)。
- **可以降级**:BayBay 流式→非流式转圈;评论/回复 Push→站内通知;搜索→只留分类筛选;官方认证申请→引导到 web;指南→bundle 内置;Onboarding→单屏。
- **不能降级**:私信/请求/被同意三类 Push(产品命脉)、删除账号(拒审)、举报+屏蔽(拒审)、联系方式检测与拦截(核心差异化)、联系卡片体验。
- **最少开发能力**:1 名 SwiftUI 中级 iOS 开发(全职)+ Will 兼后端(Node 加 API + APNs)+ 设计可用本蓝图直接开工。
- **单人是否现实**:单人全栈 90 天做完 P0 **紧但可行**,前提是:严格不加需求、BayBay/搜索先降级、用 AI coding assistant 提效。更稳的说法:单人 90 天到 TestFlight,110–120 天上架。
- **AI assistant 分工**:适合交给 AI——DesignSystem 组件、各 View 布局、Model/decode 层、APIClient 模板、空态/错误态、单元测试;必须人工把关——Keychain 与登录态迁移、Socket 生命周期、Push 落点路由、联系请求状态机、删号流程、支付敏感的合规文案、以及一切和"信任机制"有关的边界条件(冷却、拦截、可见性)。

## 二十一、最终建议

1. **BAYLINK 现在适合做原生 iOS App 吗?** 适合,且时机刚好。机制闭环(发帖/私信/请求/验证/举报)已在 web 端跑通,API 齐全度约 80%;而 web 的两个天花板——Push 召回和聊天体验——恰恰是原生的强项。BAYLINK 的核心事件(收到私信/请求)天然依赖 Push,没有原生 App,闭环永远漏气。
2. **第一版直接 SwiftUI 值得吗?** 值得。目标用户几乎全是 iPhone(湾区华人 iOS 占比极高),不需要 Android 同步首发;SwiftUI + iOS 17 起点开发效率足够高;你要的差异化体验(流式 BayBay、原生 Photo Picker、联系卡片、Push 直达)在 WebView 里都是二等公民。
3. **对比 Capacitor:** 优势——Push/DeepLink/键盘/手势/滚动全是原生质感,审核风险低(4.2 最小功能条款对壳 App 越来越严),长期技术债少;成本——需要 Swift 能力、双端(web/iOS)功能同步维护成本、首版工期比套壳多 3–4 周。结论:多花的 4 周买的是"这是个真 App"的用户感知,值。
4. **最该先完成的 5 个模块:** ①Auth+APIClient+Keychain(地基)②首页 Feed+详情页(消费侧)③发帖+BayBay+联系检测(供给侧)④私信+联系请求闭环(命脉)⑤Push+DeepLink(召回)。这 5 个串起来就是北极星漏斗,其余都是配菜。
5. **哪里做错会变成普通发帖软件:** 把 BayBay 做成聊天机器人 Tab(而不是嵌在发帖里);联系方式拦截做成"可跳过的建议"(机制一破,信任叙事全塌);消息中心做成普通 IM(丢掉"会话绑定帖子"的上下文);首页做成纯时间流文字列表(退化成 Craigslist);Push 做成营销轰炸(卸载率起飞)。
6. **哪里做对会变成湾区华人高频入口:** 私信/请求 Push 的 100% 可靠(用户为"有人找我"回来);"一句话发帖 <60 秒"的极致供给体验;联系卡片→复制→跳微信的三步顺滑(尊重微信习惯而不是对抗它);指南→发帖的漏斗(冷启动内容变现为供给);徽章与安全提示营造的"这里没骗子"体感。高频不是靠功能多,是靠"每次有人找我,我都会打开它"。
7. **给 Will 的最终执行建议:** ①本周先干后端:upload API、device token、unread-count、delete account、APNs 管线——这些不动,iOS 端 W5 就会堵死;②iOS 工程从 DesignSystem 和 CreatePostFlow 起步,先把"一句话发帖"做到惊艳,这是 demo、融资、拉新的通用弹药;③TestFlight 阶段只拉湾区真实微信群用户,盯一个数字:**每周成功建立的联系数**;④web 端从此冻结大功能,只修 bug——90 天内所有产品精力给 iOS;⑤提审材料(demo 账号、Review Notes 三段说明、删号入口)在 W9 就备齐,不要 W12 现写。
