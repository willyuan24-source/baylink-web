范围：前端 release 工作树 `25ab971a`，后端 service-booking-api 工作树 `e89b614`。只用代码检查、本地合成数据和定向测试；未创建生产业务资料、调用真实短信或修改生产用户。未审查或修改 OPUS / 3D。

## 本轮修正

1. **预约通知的失败结果在重新进入页面后消失。** 后端 `/service-bookings/me` 已提供记录的通知结果，前端原来只显示刚执行动作的临时通知。现在在对应预约卡片显示站内通知失败、待处理、短信结果未知或未配置；保留真实预约状态和消息入口，刷新确认恢复后移除警告。成功提交短信仍不称为手机收到。
2. **成员讨论明确失去访问权限后仍显示旧消息。** 讨论 GET / POST 返回 401、403 或 404 时清理已读取消息和举报面板，停止显示发送框；再次刷新需要重验讨论访问和最新小队版本，才能继续。临时网络失败仍保留未发送草稿，同一账号恢复权限后草稿可继续使用。服务端原本已阻止失权后的读取和发送，此修正补齐客户端状态。
3. **预约数据的显示时间与时间戳没有交叉核对。** 解码现在核对 `America/Los_Angeles` 日期、24 小时时分与 UTC 时间戳，限制可表示的日期范围、设置枚举及通知状态。阻止错误时刻被展示为可预订时段，防止异常期限令日期组件崩溃。预约提交结果还须匹配当前顾客及帖子服务者，才显示回执。
4. **预约核验提示只提手机号。** 修正为手机号验证或平台资料核验，与既有后台资格一致。短信提醒仍必须使用已验证手机号和真实配置，没有降低或新增资格要求。
5. **明确日期附带星期被误当成两个日期。** 搜索解析将紧邻的日期与星期视为一个日期，并核验星期是否正确。以湾区日期 `2026-09-30` 输入「10月17日周六」得到 `2026-10-17`，不再额外推断成 `10月3日`。真实备选日期仍保留多日期提示。计划页同文案的错误实际来自后台 `planner.js`，已交后台负责人修正和验证，不把前端搜索修复当作计划后台已上线。

## 复查确认的现有约束

- 服务发布者设置预约：当前手机号验证或已通过的平台资料核验；更换手机号未完成新验证不能沿用旧手机号资格。顾客须登录，未额外要求手机号。预约短信独立 opt-in，默认关闭，配置及当前手机号均须符合要求。
- 时段使用洛杉矶时区，夏令时重复或不存在的时刻由后台拒绝。待确认预约占用完整时段；跨同一服务者不同帖子检查重叠和缓冲，CAS 防止同时预订最后时段。申请不等于确认，服务者确认、拒绝、取消及完成分别有独立状态。
- 小队申请与已加入分开。候补不占席、不自动加入；空位仍需发起人确认。关键安排变更后成员需重新同意，才能发言或导出有效日历。满员、取消、已结束或屏蔽发起人不应堵住退出入口。
- 公开小队 DTO 不含申请备注、完整成员列表、邮箱或手机号。当前已确认成员方可读讨论；发起人可管理被屏蔽的成员，普通成员仍过滤被屏蔽人员。退出成员只能举报此前可见的历史消息，不能重新读取讨论。
- 重试采用同意图幂等编号，网络不确定状态不假称成功。账号/令牌变化或卸载后，旧请求不能把私人结果写入新会话。短信发送结果不确定时不自动重发。
