# 服务预约：本轮边界与下一轮设计

核对日期：2026-09-30。本文记录服务预约的实现、验证边界与官方产品研究。真实预约短信仍需另行配置和实机验证，本轮没有发送真实短信。

## 本轮流程

服务提供者完成手机号验证或 BAYLINK 平台资料审核后，可以主动开启预约，发布可申请时段。默认路径是“顾客选择时段并提交备注 → 待提供者确认 → 提供者确认或拒绝”。只有提供者明确开启即时预约，且提交时仍符合可用时段及冲突规则，才直接确认。

- 本功能不收取服务款项，不收定金，不处理退款。价格、范围与付款安排由双方确认。
- 手机验证与平台资料审核分别说明实际核验内容；不使用容易理解成政府背书的笼统“官方认证”。
- 顾客备注、预约时间与状态仅向该预约双方提供，不作为公开预约名单展示。备注应只包含安排服务所需信息。
- 待确认不能显示“预约成功”。待处理申请暂时占用时段；到期、取消或拒绝释放占用。
- 双方可取消。当前没有一次操作完成的改期；先沟通、取消旧预约、再申请新时间，新申请没有成功前不能承诺新时间已确认。
- 提供者可以在已确认预约结束后标记完成；时间经过不自动证明服务履行。
- AI 可协助整理需求、翻译与草拟回复，不自动接单，不承诺上门时间、任务范围或报价。

## 已确认的默认值与状态

| 项目 | 本轮约定 |
| --- | --- |
| 预约总开关 | `enabled=false`，由服务者主动开启 |
| 预约模式 | `mode=request`，服务者可选 `instant` |
| 时区 | `America/Los_Angeles`，保留时区而非固定 UTC 偏移 |
| 最短提前时间 | `minNoticeMinutes=120` |
| 缓冲设置 | `bufferMinutes=30`，可选 0/15/30/60；任意两份有效预约之间取各自快照缓冲值的较大值，不前后重复累加，不当作真实驾车时间估算 |
| 待确认到期 | `expiresAt=min(createdAt+24h,startAt)` |
| 完成 | 已确认预约结束后由提供者主动标记 |
| 付款 | 平台不收取服务款项 |

并发提交、重复点击、取消与到期后的占用释放应由后端确保一致，不能只依赖页面隐藏按钮。修改未来可用时段不应悄悄改动已确认预约。

当前时段边界：每段 15 分钟至 12 小时，必须在同一洛杉矶当地日期内；最多提前 180 天，最多 300 个未来时段，单次批量 1–30 段。同一提供者跨帖子不能发布原始区间重叠的时段。相邻时段可以发布，但其中一段被预约后，邻近时段会按缓冲规则变为不可预约。后端拒绝洛杉矶夏令时切换产生的不存在或重复本地时间。

## 通知与短信的实际范围

站内预约记录与相关消息用于查询处理结果。短信只是另行选择的通知渠道；失败或暂不可用不丢失预约。

当前业务短信只发给提供者，事件范围为顾客新申请、即时预约及顾客取消。顾客不接收预约短信；确认、拒绝、完成等其他处理结果依照站内状态与通知展示。当前没有定时到场提醒或营销短信。

短信同意与手机验证码同意完全分开。提供者短信设置保存：

- `enabled`：是否开启业务短信。
- `consentVersion='service-booking-sms-v1'`。
- `consentedAt`：同意时间。
- `verifiedPhone`：同意对应的已验证号码，仅内部使用。号码变化后须重新同意。

发送前需要已验证手机号、有效独立同意，以及启用且完整配置的短信服务。后端契约要求 `SERVICE_BOOKING_SMS_ENABLED=true`、`SERVICE_BOOKING_SMS_OPT_OUT_CONFIGURED=true`、Twilio Messaging Service SID 和所需 Twilio 配置。没有配置时显示不可用，不能假装已发送。

当前退订使用已配置并验证的短信供应商 STOP 抑制机制；没有新增自写 STOP webhook，不绕过供应商 `21610` 退订阻止。提供者可以在站内关闭通知；重新开启站内开关不能清除发送方退订状态。短信 adapter 接受请求只表示“短信已提交”，不表示已送达，页面与条款均不作送达保证。

手机号不因验证或开启通知而公开。发送业务短信时，短信供应商会处理接收号码与通知内容；不把顾客完整服务备注塞入短信。

## 官方研究与采用理由

1. [Cal.com：Requires Confirmation](https://cal.com/blog/reclaim-your-time-setting-up-requires-confirmation-in-cal-com) 支持由服务者明确接受后才加入日程。维修、清洁和接送的任务规模及路程具有不确定性，本轮选择人工确认作为默认。
2. [Taskrabbit：预约后的沟通与排期](https://www.taskrabbit.com/blog/getting-started-with-taskrabbit-what-happens-after-i-book/) 强调先确认技能、工具、任务范围、地址、停车与进入方式，再排期。BAYLINK 采用任务备注与站内沟通，不复制其收费或取消费政策。
3. [Calendly：前后缓冲](https://calendly.com/help/how-to-use-buffers) 将准备、交通和收尾时间纳入冲突判断，并说明缓冲可能延伸至工作时间之外。BAYLINK 应明确可用时段与缓冲边界，不能把固定缓冲描述成已核验的交通时间。
4. [Acuity：短信提醒与独立选择](https://help.acuityscheduling.com/hc/en-us/articles/16676915777293-Sending-appointment-reminders-via-text) 区分预约和短信同意，允许选择退订，并说明供应商发送不保证送达。本轮将这种独立选择原则用于提供者业务短信，不复制客户定时提醒功能。
5. [Acuity：服务者与员工通知](https://help.acuityscheduling.com/hc/en-us/articles/16676918220173-Send-appointment-notifications-to-yourself-and-your-staff) 区分通知渠道和通知类型，也提示重复通知风险。本轮站内记录作为稳定入口，短信按事件去重，失败不改变预约结果。

这些来源用于产品交互参考，不用于宣称 BAYLINK 具备其全部功能，也不构成关于短信法律要求的完整结论。

## 下一轮

- 原子改期：新时段获得双方确认并成功占用后，再释放原时段；有清楚的旧时间、新时间及等待对方状态。
- 外部日历冲突同步、员工/资源排班、重复清洁预约及候补。
- 依据服务地点和交通方式估算动态缓冲；跨湾、停车和航班变化由服务者复核，不能由 AI 自动承诺。
- 顾客独立选开的短信与定时提醒，在明确同意、退订、发送状态和去重机制后再开放。
- 按服务类型提供少量结构化需求：维修问题/照片、清洁范围/用品、接送起终点/人数/行李。地址和进入方式应只对必要的预约参与者可见。

## 实际入口与排期助手

- 发布服务成功后，可直接进入该帖设置可预约时段。已发布服务的作者也能从详情页管理预约设置与批量排期。
- 个人主页与消息页均提供“服务预约”入口，集中查看“我预约的”和“我收到的”。
- 快速排期支持固定格式，例如“10月17日周六 09:00-12:00”“下月每周六 09:00-12:00”。先显示具体日期，再加入待发布清单，最后明确发布。未写年份时采用当前年份，并检查日期与星期是否一致。
- 该助手是本地规则解析，尚非自由对话 AI 排期。不能理解的复杂语句、例外日期不会被悄悄忽略；需要用户改写或手动添加。服务器最终检查时区、提前时间、时段长度与冲突。
- 每个发布区间是一笔完整预约，不会自动切成多个小时名额。目前不支持员工人数或多人容量。

## 本地验收与上线边界

在隔离的内存 API、三个虚构演示账号和本地 Vite 页面中验收，不读取或写入生产预约：

1. 顾客选日期与时段、填写服务城市及需求，提交后显示待确认。
2. 服务者收到申请并接受，双方的站内会话出现申请与确认记录。
3. 服务者取消后，原时段重新出现在可约清单。
4. “10月17日周六 09:00-12:00”成功预览为 2026-10-17，并经两步确认加入发布列表。
5. 390×844 手机视窗没有横向溢出；未配置短信时开关禁用，并说明站内预约仍可使用。

自动化覆盖前后端预约状态、抢同一时段、跨帖子冲突、重试去重、验证权限、短信独立同意、切换账号、中文/繁体/英文、日期解析及已有发布/路由流程。TypeScript 检查与隔离目录的 Vite 打包通过；本轮没有运行会重新生成全站资讯和 3D 资源的完整发布流水线。

上线需要同步发布前后端并初始化 `ServiceBookingAgenda` 模型。短信另需运营方配置 Twilio Messaging Service、凭证及已验证的退订处理，启用 `.env.example` 中两项预约短信开关，再进行受控实机验证。当前代码不会借用登录验证码发信号码。

本轮使用每位服务者一份带版本的预约文档作原子冲突控制；每位服务者最多保留 2,000 笔预约和 4,000 个新增操作幂等记录。达到上限会明确拒绝新增，不覆盖旧记录，也不阻止已有预约的确认、取消、拒绝或完成；每笔预约另存最多两条动作幂等记录。扩大使用前应加入归档、独立通知任务与容量监控；当前通知补发依赖后续相关请求，不是持续运行的后台投递队列。

首轮相关测试共 114 项通过（前端预约 14、排期/发布/个人页/路由等 31、后端预约 15、后端既有相关回归 54）。这是初版记录；第二轮在最新主分支重新整合并进行完整发布检查。

## 第二轮易用性与上线复查

- 服务者先看到开放/暂停状态与时段；确认模式、提前时间和缓冲放在可选规则中。快捷开关只更新开放状态，不会顺便保存未提交的高级规则草稿。
- 预约暂停后，已保存时段仍可管理；保存时段与开放预约分别说明，避免把保存误认为已经对顾客开放。
- 顾客提交前显示完整日期和起止时间，明确整段预约与待确认含义。网络错误提供重试；时段冲突后刷新保留需求输入。
- 通知失败与预约保存结果分别呈现，避免重复下单。预约系统消息有专属标识和“查看预约”入口，不显示无法使用的引用、回应与翻译按钮。
- 只有收到预约的服务者通过通用通知链接进入时，默认看到“我收到的”；用户主动切换的方向予以保留。
- 预约深链 `/me/bookings` 与尾斜杠版本加入生产路由，并设置 `noindex` 和 `no-store`。未知子路径仍返回 404。
- 换号发起新的验证后，旧验证标记不能用于预约短信授权；确认时再次检查有效期，避免授权检查期间到期仍被接受。
- 发布以最新远端主分支为基础，保留既有 OPUS-Bay、学校指南及资讯更新。顺带修复原有四项站点检查失败：水灯图片及缩图、来源登记、四条准备事项的标题、圣何塞新增活动的精确筛选预期；没有删去第四条内容。
